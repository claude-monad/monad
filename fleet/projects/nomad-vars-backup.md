# Automated backups for the Nomad variable store (the cluster's own secrets + state)

## Goal
Give the **Nomad variable store** the same automated, retained, restorable backups that
[[postgres-backup]] and [[registry-backup]] already give Postgres and the registry. The
Nomad KV holds 67+ variables, including the cluster's **secrets** (`secret/agent-mesh`,
`secret/conductor`, `secret/fleet`, `secret/samba`), infra credentials (`infra/postgres`,
`infra/registry`, `infra/storage`, `nomad/jobs/{postgres,minio-storage,cluster-conductor}`),
and ALL fleet coordination/health state (`fleet/*`, `monad/maintenance/*`, messages, task
results). Today the only copy lives in Nomad's Raft state on the servers.

## Why
Postgres and the registry are backed up; the Nomad variable store — which is *more*
load-bearing, since it stores the cluster's credentials and every health/coordination
signal — is not. If Raft state is lost (disk loss on the servers, a bad bootstrap, an
operator wipe like the 2026-06-02 claudebox orphan teardown), **every secret and every
fleet coordination var is gone with no recovery path**: postgres/minio/conductor creds,
agent-mesh creds, and the entire fleet health picture would have to be regenerated by hand.
This is pure infra hygiene, fully additive: the job only **reads** variables via the Nomad
HTTP/CLI API (ACLs are disabled cluster-wide, so a read needs no token) and writes
compressed dumps to a **new** directory it owns; it deletes nothing it did not create
(retention prunes only its own dumps).

## Placement
Pinned to **bigo-server** via `node.unique.name` + `driver.raw_exec`, alongside the other
backups and [[backup-health]] (which already runs raw_exec + python3 there and has the
`nomad` CLI on PATH). Dumps land in a host bind-path `/opt/monad-vars-backups` on the same
node, mode `700`, files mode `600`.

**Sensitivity caveat (important):** unlike a registry tar, this dump contains **plaintext
secrets**. The cluster has no documented at-rest key/passphrase mechanism (and bootstrapping
one is circular — the key can't live only in the store being backed up), so v1 stores
plaintext on a tailnet-internal, root-restricted node with strict perms (dir `700`, file
`600`), exactly the trust posture of the other on-host backups. At-rest encryption (e.g. an
owner-provided GPG recipient / age key) is a sensible **owner-gated follow-up**.

## Acceptance
- A periodic Nomad job `nomad-vars-backup` enumerates every Nomad variable and writes a
  compressed, timestamped, **verified** dump to `/opt/monad-vars-backups` on bigo-server.
- The dump captures each variable's decrypted `Items` (so it is actually restorable), in a
  format a restore loop can replay (`nomad var put -in=json`).
- Verification: the run re-reads its own gzip, parses it, and confirms the dump holds at
  least as many variables as the live store reported (fail + keep `.partial` otherwise).
- Old dumps are pruned to a retention window (keep ~14) — pruning only the job's own dumps.
- Dump files are mode `600` in a mode `700` directory (plaintext-secret hygiene).
- The new backup is part of the single fleet health signal: [[backup-health]] checks the
  vars-dump family too, so a stale/missing vars backup shows up in `fleet/backup-health`
  (and thus the [[fleet-health-rollup]] `backup=` component + dashboard).
- Verified by forcing one run and confirming a non-empty, valid `*.json.gz` appears whose
  parsed contents include known paths (e.g. `secret/fleet`, `infra/postgres`).
- Docs: the project Log records where dumps live, the schedule, and the restore procedure.
